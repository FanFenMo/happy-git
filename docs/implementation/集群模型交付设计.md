# 第三轮服务端交付设计

本轮从第二轮集中验收后的 develop 开始，保持现有 Java MapReduce、HDFS、ZooKeeper 任务租约、MySQL 模型与画像指针。A 维护数据平台、业务服务和部署工具；客户端、正式数据生成与独立大模型评测由 B 接续。功能分支只做编译、生成和静态自查，实际 YARN 训练、双机并行、故障恢复与正式数据验收在相关功能进入 develop 后集中执行。

部署采用由主机清单生成角色配置、由已构建 JAR 生成版本包、由明确节点安装及切换版本的流程。配置中的安装根、数据根、服务用户、业务 API 节点和 JDK17 路径均来自清单。版本包保存代码提交和文件摘要，复制环境样例时保留既有私有配置，安装与版本切换不格式化 HDFS、不清理归档、不自动重启生产服务。两主机模式继续标明控制面单点，三主机及以上仍需真实多数派和 fencing 验收。

模型运行增加文件型导出入口。协议冻结数据描述符、目录、模型、referenceTime、split、用户范围和分块；规则基线与学习模型使用同一可用证据与已冻结特征空间，结果输出独立 JSONL，保留实际方法、模型和证据引用。导出包附输入摘要、运行耗时、用户数、向量规模、Hadoop 参数和作业索引。正式测试用户不会因导出而进入训练或参数选择。

每个 MapReduce 阶段在提交与完成时记录实际 job/application、输出路径、开始结束时间、计数和资源配置，失败或取消也保留记录。证据采集工具只读取这些确切作业，在 ResourceManager、HistoryServer 和 NameNode 查询实际节点、资源、task attempt 与数据可读状态。双机并行结论要求同一作业内不同节点成功 attempt 的时间重叠，配置数量和在线 worker 数不代替作业证据；接口未就绪或节点缺失时保留未完成原因。

任务恢复继续使用原租约和独立尝试目录。管理员只能操作明确命名空间及任务，取消绑定已观察到的尝试次数，运行中的任务在阶段等待和发布前检查租约与取消状态，并只终止自己提交的 YARN 作业。重试创建带原任务关联的新任务，原失败、取消及作业证据保留，模型与画像发布仍使用现有事务指针。

交接提供版本包、冻结协议样例、文件导出结果契约、实际部署观察、集中验收步骤以及模型发布、回退、指定服务启停和任务接续说明。源码完成、编译完成、实际部署和集中验收分别记录，后续正式数据与 B 的端上操作产生后再填入真实模型和运行索引。
