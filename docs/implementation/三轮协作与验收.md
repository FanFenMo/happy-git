# HappyGit 三轮协作与验收

日期：2026-11-08。两位开发者分别按甲、乙承担[功能模块任务表](功能模块任务表.md)的模块。本页组织每轮交接、集中验证和最终交付，不表示已经执行这些步骤。

## 第一轮：准备数据并接通个人数据入口

甲首先维护统一契约和服务端迁移，随后并行推进批量项目采集、公开关系关联项目补抓、云端身份及事件持久接收。采集任务一旦具备条件即可由管理员启动，供后续工具逐步取得真实目录；不必等整个应用服务开发结束。

乙先修复现有推荐契约与DTO问题，并实现数据集组装和校验工具。在客户端保留既有聚合历史，新增逐次有效事件、上传队列、云端状态及两端原生适配。开发初期可以使用明确标记的格式样例和固定业务响应，轮末用甲的真实接口替换联调。

第一轮开始时共同核对Ubuntu主机、公开采集访问方式、云端GitHub身份配置和Android验收设备。服务地址及凭据配置由维护者处理，普通用户不填写。外部条件未落实时可以继续模块开发，阶段状态保留未完成的实际部署与真机事项。

第一轮交接由甲提供冻结目录样本、业务接收地址、设备与ACK契约、归档证据；乙提供可导入数据包、evidence-view、两端上传队列和现有推荐问题修复。两个主PR及必要修复进入develop后集中验证。

| 集中核对 | 需要观察到的结果 |
| --- | --- |
| 批量采集 | 实际公开项目与README进入HDFS，集合完整性与覆盖可追溯，关联项目有补抓任务 |
| 数据工具 | pilot实际文件、counts/hash及来源可核对，按用户拆分，runtime没有隐藏答案 |
| 事件产生 | 一次有效浏览对应一次聚合计数和一条逐次事件，快速重复打开不额外增权 |
| 云端接收 | 同一事件重发得到相同确认，接收身份与账号一致，客户端确认后不误写入别的账号 |
| 归档接续 | 已接收事件能追到闭合HDFS文件，接收与处理进度分开，集合和来源转换正确 |
| 数据保留 | SQLite迁移保留原有账号、历史与缓存；关闭云端分析后停止上传 |

第一轮通过的含义是数据入口和持久链路成立。此时尚不能把客户端显示的开发画像当作已训练模型结果。

## 第二轮：完成初始训练、个人推断和回流更新

甲在训练用户上拟合制品并学习兴趣中心，使用验证用户选择配置，形成第一版模型。随后实现加载固定模型的个人推断、同代结果发布，以及从新增行为重建训练样本、产生下一版候选模型的过程。管理端可以看到训练、推断、回流来源、模型验证与发布状态。

乙根据约定输出缓存云端画像，生成并执行有界搜索计划，接通两端搜索结果、近期行为排序、个人和群体页面。同步实现独立评测运行器的输入输出、哈希核对、指标计算和报告结构，第三轮正式调用大模型。普通浏览器样式预览和原生端业务验收分别记录。

第二轮交接由甲提供可加载的模型、真实画像接口、搜索方向和processedThrough；乙提供真实客户端回流、搜索与排序流程，以及实验运行器。轮末先合入develop，再集中完成整个闭环。

| 集中核对 | 需要观察到的结果 |
| --- | --- |
| 初始模型 | 有实际训练作业、数据快照和完整制品，学习参数来源于训练用户 |
| 独立推断 | 测试用户和新个人数据使用已发布模型，推断不会改写中心或重新拟合词表 |
| 画像发布 | 模型、特征空间、用户证据、generation和处理进度相互对应 |
| 搜索使用 | 客户端按方向搜索真实项目，可以出现训练目录外的结果，项目字段和引用保持完整 |
| 本机接续 | 已收到但未处理的事件仍可影响本地近期排序，新画像到达后不重复累计 |
| 回流再训练 | 至少一个真实客户端回流批次进入下一版训练清单，保存对应行为和旧画像版本关联 |
| 模型换版 | 新模型通过验证后发布，当前指针改变；旧模型和旧画像仍可追溯，必要时可回退 |
| 界面与账号 | 待处理、空证据、旧结果、群体来源和账号切换反映实际状态 |

模型更新这一项必须真实执行一次“初始模型—个人使用—新证据归档—再训练—验证—发布—再次推断”。仅创建第二个版本号不算完成。真实回流规模可以从小样本开始，报告实际样本量，不据此提前声称效果普遍提高。

## 第三轮：正式实验、多机运行和双端交付

甲把已集成代码部署到实际Ubuntu环境，运行YARN上的训练和推断，记录实际节点、任务、资源和结果摘要。按所部署模式验证必要的任务接续和数据可读性。三台及以上独立主机的高可用承诺需要对应多数派、fencing和切换证据；两台模式如实记录控制面限制。

乙在固定测试用户上运行旧基线、当前学习模型与独立通用大模型。调用只使用共同证据及公开taxonomy，不附隐藏设定和算法输出，保存准确模型标识、提示词、输入哈希、原始响应及失败。正式测试完成后对固定子集重复调用，报告波动。

实验主要评价技术兴趣画像：Top-8标签一致性、语言和主题分布、证据引用及无证据处理。另做匿名证据核查，报告各场景、来源和稀疏程度的样本数。大模型作为独立方法，报告中的相似程度不直接等于准确率。项目推荐仅做真实链路和少量任务样例验证，不把它扩展成另一套大规模推荐研究。

模型参数在validation选择，正式test不用于反向调权重。持续更新模型时，保留初始独立测试基准，并另记录近期数据的评测协议；训练输入、评测用户或观察时间变化后，结果分别标记，避免把不同实验拼成一个改进百分比。

乙生成绑定同一提交的Windows与Android安装包，在目标环境核对首次安装、保留旧数据的升级、云端身份、上传、画像、搜索、Star/取消Star及退出。真实GitHub写操作只在明确指定的测试项目中进行并恢复初始状态，安装与原生业务使用记录不能由网页预览替代。

第三轮结束前共同从干净启动流程完成演示：查看采集来源，查看首版模型，客户端产生个人数据，离线生成画像并搜索项目，再查看一批回流训练及下一版模型的来源。演示可以用事先实际完成并保存的训练记录解释耗时，但界面须明确哪些是已完成历史任务，哪些是当前运行。

## 集成和分支规则

功能分支从develop创建，同轮每人的主PR可包含多个相关模块。提交与PR标题使用实际功能名称，例如“支持客户端画像搜索与近期排序”。既有缺陷和集成验收发现的问题使用独立bugfix分支，修复合回develop后做对应复验。

开发分支完成必要的编译、格式与实现自查；整套功能和集成测试放在相关功能合入develop后按轮集中执行。没有新修改、失败或未解决问题时不重复扩大测试范围。正式实验本身也按冻结协议运行，不在每个提交后重做大模型调用和全量训练。

合入顺序先确保共有契约和已有缺陷修正可用，再集成服务端与客户端增量。两人各自在独立分支或工作目录开发，不在同一工作目录并发切换分支。交接包含基线提交、修改路径、实际接口、完成模块、未完成事项和复现方式。

main只接收完成集成与发布验收的版本。本页不授权提前合入main、推送或发布远端产物；这些动作按届时用户指令执行。普通本地实现与修复继续在既定分支规则内推进。

## 最终交付材料

| 交付部分 | 内容 |
| --- | --- |
| 代码与版本 | 最终develop提交、功能与修复PR、服务端/数据平台/双端对应版本 |
| 数据 | 初始训练/验证/测试包、真实来源说明、回流批次清单、实际校验和证据视图 |
| 模型 | 至少一次初始训练和一次回流再训练的制品、来源、配置、验证及发布记录 |
| 实验 | 基线、学习模型与独立大模型结果、原始响应、指标脚本、分场景报告和实际失败 |
| 部署 | 实际主机清单、服务配置、运行/停止/恢复步骤、跨节点作业及能力边界 |
| 应用 | 新EXE/APK、版本摘要、安装与升级记录、真实使用证据 |
| 文档 | 项目方案、接口与模型契约、模块任务状态、数据生成规范、实验报告、部署与演示指南 |

最终整理时移除沟通用临时文件名前缀并修复链接，正文、代码、提交和PR保留功能名称。历史实现记录保留其日期与真实结果，入口指向当前有效说明。Git历史不为移除口头编号而重写。

项目完成需要持续学习闭环、双端业务、实际部署和画像实验均有证据。若某项外部条件仍未落实，在任务表保留对应未完成状态，其他已完成模块可独立交付；不把代码集成、模块验证和正式实验合成一个笼统百分比。
