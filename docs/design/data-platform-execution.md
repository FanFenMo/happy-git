# 数据采集与 Ubuntu 集群处理执行设计

2026-11-03，承接已审阅的 Hadoop 数据主线。本轮用户明确要求先执行采集与处理，先在本机 Ubuntu 验证，随后部署到约 2—4 台 Ubuntu 主机，同时按已安装的 b-end-design-system 重设计管理端与客户端。

实现分为独立 Java 数据平台、Ubuntu 集群部署工具和双端界面设计。Java 数据平台使用 HDFS 存不可变采集批次与计算产物，YARN 分配 MapReduce 任务，ZooKeeper 保存有版本的任务状态、临时执行租约和完成指针。采集 worker 可在每台主机运行：任务领取和完成使用版本比较与事务，进程故障后的任务由存活 worker 接续；原进程复活不能发布过期尝试。HTTP 抓取不放入 Mapper，避免 task 重试重复访问 GitHub。

本轮的任务控制使用 ZooKeeper，独立于尚未实现的用户业务 MySQL。该选择服务于“数据平台本身不依赖一个单点任务数据库”，不表示个人账号与推荐在线表已经迁移。采集仅覆盖公开仓库元信息、README、公开集合和活动；输入行为明细通过受控 CLI 导入，用户云端授权上传 API 留在后续接入阶段。

三台及以上主机使用两个 NameNode、两个 ResourceManager、三个 ZooKeeper/JournalNode，以及各主机 DataNode/NodeManager。NameNode 自动切换使用 ZKFC、QJM 与 fencing；ResourceManager 使用 ZooKeeper 状态恢复和自动选主；任务失败由 YARN 的 task/AM 重试接续。三节点仲裁在多数派存活时容忍一节点故障，数据副本和剩余计算资源也是继续处理的条件。

两主机无外部仲裁的配置只能提供数据副本和计算工作节点失败后的任务重试，控制面有单点，必须在部署输出与界面显示“受限模式”。不能将两个物理主机上的三个进程宣称为可容忍任意一物理主机故障的仲裁集群。要达到相同自动切换能力需第三独立节点，或扩充到三台。

部署工具读取 Ubuntu 主机清单，生成每节点 Hadoop/XML、ZooKeeper、systemd 和环境配置；主机名、SSH 别名、数据路径、内存和监听地址参数化。默认不格式化已有 NameNode、不删除数据、不对正在使用的服务注入故障；初始化及故障演练显式选择隔离环境。

UI 采用统一语义 token、浅底状态标签、单操作区唯一主按钮、查询区与数据区分离、加载/空/错误/受限/成功五态。管理端围绕采集任务、运行批次、真实节点与输入覆盖；客户端围绕推荐、用途、项目证据与个人记录。详情采用成熟组件抽屉，表单不允许遮罩误关闭。未知集群或画像数据明确为空，不显示伪造健康节点和推荐分数。

按项目约定在 feature/server-data-cluster 开发和编译，集成到 develop 后集中验证。记录本机实验环境与真正多主机验收的区别；只有实际执行过的故障接续才报告已验证。
