# 新 HappyGit 第一版客户端详细设计

版本 1.0，2026-10-29。本文把现有 Vue、Electron、Android 工程改造成读取 Hadoop 结果并在本机调整推荐的客户端，整体边界见[总览](README.md)，参数见[接口与数据契约](接口与数据契约.md)。下面的“保留/改造”指实现时的计划，不表示本次已经修改对应源文件。

## 1. 页面后面的四层职责

Vue 负责显示和交互，Pinia 保存当前页面状态；service 负责组织一个用户动作；原生层负责凭据、HTTP 和 SQLite 事务；Web Worker 负责纯计算。正式长期画像来自服务端，`computeAndCommitProfile()` 不再进入正常推荐链路。原 `profile.js/recall.js` 可作为隔离实验基线保留，但页面失败时不偷偷切回它们。

## 2. 原生桥、登录与跨平台调用

`client/shared/contracts/index.js` 增加 CLOUD_SYNC_READ_STATE、CLOUD_SYNC_FLUSH、CLOUD_RECOMMENDATIONS_REFRESH、CLOUD_PORTRAIT_READ、CLOUD_COHORTS_READ、CLOUD_PRIVACY_REQUEST。`recommendation.createSnapshot/commit/list` 保留名称，但 `purpose="rerank_v2"` 明确选择新契约。Electron preload 白名单、ipc-router、Android HappyGitPlugin 和两个 JS adapter 同步使用这些操作名。

`ipc-router.handle(operation,payload,contextId)` 只从原生 SessionManager 取 accountId；个人操作必须同时核对 contextId 和当前账号。异步 HTTP 返回以后、交给数据库写入之前再核对一次，因为等待期间用户可能已经换号。`platform/index.js.invoke()` 的个人操作判断补充 cloud.*，保持迟到响应不进入 Vue；原生端校验仍是最终写入边界。

`CloudClient.request(routeName,body,sessionContext)` 由原生内部使用固定 routeName→method/path 映射，基地址来自打包配置。加上当前应用 access token 后请求；遇到 access 过期，调用同一 session 的 single-flight `refreshSession()`，成功后最多重发原请求一次。POST/PUT 重发必须具备 eventId/seq 或 mutationId 幂等身份，不能对不确定的 GitHub Star 写入套用该规则。

`CloudSession.beginLogin()` 调用服务端 begin，在原生保存 pollProof，打开 authorizationUrl；`pollLogin(taskId)` 按服务端间隔领取应用凭据；`activateSession(result)` 安全保存 refresh token，设置新的 contextId，初始化对应 SQLite 账号；`logout()` 撤销服务端会话并清当前原生凭据，终止该上下文 Worker/上传任务，保留用户未选择删除的本机历史。

Electron 的 `CredentialStore.save/load/delete(accountId)` 在主进程使用本项目锁定 Electron 版本支持的 safeStorage 接口，加密字节写入应用数据目录，业务 SQLite 只保留账号及凭据引用。Android 的同名方法用 Android Keystore 中的 AES-GCM key 加密 token，保存随机 IV 与密文；Keystore 保存密钥，不直接存 token 文本。底层能力依据 [Electron safeStorage](https://www.electronjs.org/docs/latest/api/safe-storage) 和 [Android Keystore](https://developer.android.com/privacy-and-security/keystore)，实现时按仓库实际运行版本选择可用 API，不直接复制较新版专有方法。

网页 GitHub 会话独立保留。`StarService.set(repo,desiredState,context)` 执行之前比较网页识别的 GitHub accountId 与应用服务端 accountId，匹配才操作，否则要求切换网页账号。推荐、同步和打开项目不会隐式调用 StarService。

## 3. `recordBrowse()`：历史、逐次事件与 outbox 怎样一起产生

当前 `database-worker.cjs:655` 的 `recordBrowse()` 已使用 `last_counted_at` 实现 30 秒计数；此规则保留。新增逐次事件只在 shouldCount=true 时产生，30 秒内重复打开更新 last_viewed_at，却不重复增加访问次数或向量贡献。

`projects.openRepository(repository,source)` 继续发 `repository.open`。原生先验证目标为允许的 GitHub HTTPS 仓库地址，再成功发起外部打开，最后按当前账号和本机记录开关调用 recordBrowse。这里能够确认的是“发起打开”，不能声称知道外部网页是否加载完成或用户停留多久。

下面代码为数据库 worker 内核心实现，`repo` 已由原生边界标准化；所有 SQL helper 共享同一个同步 SQLite 连接与事务。

```js
function recordBrowse(accountId, repo, source, now) {
  return withTransaction(() => {
    const prefs = readLocalPreferences(accountId)
    if (!prefs.historyEnabled) return { counted: false, historySaved: false }
    const key = repo.repoId || repo.canonicalKey
    const old = readHistoryRow(accountId, key)
    const counted = !old || now - old.lastCountedAt >= 30_000
    upsertHistoryRow(accountId, key, repo, source, now, counted)
    pruneHistory(accountId, now)
    bumpRevision(accountId, 'history_revision')
    if (!counted) return { counted: false, historySaved: true }

    const state = readCloudAccountState(accountId)
    const event = {
      eventId: crypto.randomUUID(),
      accountId,
      recordKind: 'open',
      deleted: false,
      localSeq: allocateLocalSeq(accountId),
      repoId: repo.repoId || null,
      canonicalKey: repo.canonicalKey,
      occurredAt: now,
      effectiveAt: null,
      source,
      analysisEpoch: state.analysisEpoch,
      deviceId: null,
      streamEpoch: null,
      deviceSeq: null
    }
    if (state.cloudSyncEnabled && state.bindingVerified &&
        state.streamRegistered && repo.repoId) {
      const stream = allocateDeviceSeq(accountId, state)
      Object.assign(event, stream)
      const payload = toOpenRecord(event)
      payload.payloadHash = hashOpen(payload)
      insertOutbox(accountId, payload)
    }
    insertLocalEvent(event)
    bumpDeltaRevision(accountId)
    return { counted: true, historySaved: true, eventId: event.eventId }
  })
}
```

`readHistoryRow` 按账号与 repo key 主键查；`upsertHistoryRow` 更新最近时间和卡片缓存，只有 counted 才增加次数、更新 last_counted_at。继续调用现有 pruneHistory 与 history_revision 更新，只裁剪聚合展示历史，不顺带删除逐次事件或 outbox。`allocateLocalSeq` 从账号运行状态取出并增加 next_local_seq；`allocateDeviceSeq` 读取当前 local_sync_state.next_seq，递增后返回 deviceId、streamEpoch、deviceSeq。两个序号都在同事务内分配，失败一起回滚，不留下已经消耗却没写出的上传序号。

`toOpenRecord(event)` 只选择契约允许上传字段，schemaVersion 固定，不能用 `{...event}` 把本机对象中的其他字段一并发送。`hashOpen()` 对固定字段数组做 UTF-8 SHA-256；`insertOutbox` 写 payload/hash 与 pending 状态；`insertLocalEvent` 写可用于本机调整的明细。ACK 成功后可以移除 outbox 正文，但 local_activity_events 仍需保留用于微调。

没有 repoId 的项目可以保留本机历史和公开文本，不能立即分配正式上传序号。`resolveLocalRepository(canonicalKey,resolvedRepo)` 只把已核验的真实 repoId 关联回本机事件和历史别名，并增加 deltaRevision；第一版不为解析前的事件补分配 deviceSeq，避免把没有上传身份的旧事件混入新授权范围。下一次有效打开才产生可上传事件。

`deleteHistory(accountId,repoId)` 和 `clearHistory(accountId)` 在同一事务内删除对应展示历史与微调事件，把相关未确认 outbox 转为 discard，只保留原 eventId、seq、hash。已在网络途中的 open 不能保证撤回，因此旧请求返回 ACK 时只按 seq 终结；UI 说明本机清空不等于云端清除。`discardExpiredOutbox(now)` 对超过保留期的未发送正文做相同终结转换，不直接跳号。

## 4. `flush()`：上传成功为什么还要保留本机增量

`CloudSyncService.flush(context)` 由累计 100 条、前台运行满 5 分钟、网络恢复或用户主动同步触发；Android 被暂停时允许延迟，不承诺进程终止后仍执行。按 accountId+streamEpoch 建 single-flight，避免一次触发启动多个相同上传循环。

`readUploadBatch(accountId,streamEpoch)` 从最早未确认 seq 开始，最多取 500 条；按紧凑 JSON UTF-8 编码实际字节数限制 1 MiB，不能只用字符串长度。相邻记录必须连续。`applyAck(accountId,ack)` 在事务里把不超过 acceptedThroughSeq 的 outbox 标已确认，更新 accepted/exported 水位，按 eventId 保存 timeAdjustments；不改 occurredAt/payloadHash，不删除尚未被画像覆盖的本机事件。

```js
async function flush(context) {
  return runSingleFlight(context.accountId, async () => {
    assertCurrentContext(context)
    const batch = await db.call('readUploadBatch', { accountId: context.accountId })
    if (!batch) return db.call('readSyncState', { accountId: context.accountId })
    const ack = await cloud.request('eventsBatch', batch, context)
    assertCurrentContext(context)
    await db.call('applyAck', { accountId: context.accountId, ack })
    return db.call('readSyncState', { accountId: context.accountId })
  })
}
```

一次 flush 发送一批，成功后调度器有积压再排下一次，避免同步 while 循环霸占原生线程。`runSingleFlight(key,fn)` 返回同 key 已在执行的 Promise，完成后从 Map 删除；`assertCurrentContext` 比较原生持有的账号/contextId。所有持久写入再携带账号范围，不能只靠渲染层“当前登录人”判断。

`handleSyncResponse(error)` 只处理真实业务分支：限流/暂不可用依据 retryAfterMs 保留队列；SEQUENCE_GAP 读取服务端 sync-state 后从 expectedSeq 重发本机保留的前缀；若本机记录确实丢失则暂停该流并显示无法接续，不伪造正文；ANALYSIS_RESET 应用新的 epoch 并终结旧流；会话失效回到登录。不要增加与上传无关的机器健康扫描。

水位例子是核心：基础画像覆盖到 100，上传 ACK 到 105，seq 101—105 仍参与本机微调。判断依据是 processedThrough，不是 outbox 是否 pending。新包覆盖到 105 时，基础和水位一起换入，下一快照自然不再选中这五条；不需要手工从上次调整向量里做减法。

Android 的对应方法放在 `nativebridge/LocalRepository.java`。下面展示同一个 ACK 事务如何用原生 SQLite 写出；`requireCurrentStream()` 在该事务内读取账号/设备/epoch 并核对当前有效绑定，`bumpDeltaRevision()` 只在实际时间修正改变微调输入时更新 revision。网络请求在调用此方法之前已经结束。

```java
public void applyAck(String accountId, IngestAck ack) {
    SQLiteDatabase db = dbHelper.getWritableDatabase();
    db.beginTransaction();
    try {
        requireCurrentStream(db, accountId, ack.deviceId(), ack.streamEpoch());
        db.execSQL("UPDATE local_sync_state SET "
                + "accepted_through_seq=MAX(accepted_through_seq,?), "
                + "exported_through_seq=MAX(exported_through_seq,?) "
                + "WHERE account_id=? AND device_id=? AND stream_epoch=?",
                new Object[]{ack.acceptedThroughSeq(), ack.exportedThroughSeq(),
                        accountId, ack.deviceId(), ack.streamEpoch()});
        db.execSQL("UPDATE event_outbox SET state='acknowledged', payload_json=NULL "
                + "WHERE account_id=? AND device_id=? AND stream_epoch=? AND device_seq<=?",
                new Object[]{accountId, ack.deviceId(), ack.streamEpoch(),
                        ack.acceptedThroughSeq()});
        boolean adjusted = false;
        for (TimeAdjustment change : ack.timeAdjustments()) {
            ContentValues values = new ContentValues();
            values.put("effective_at", change.effectiveAt());
            int changed = db.update("local_activity_events", values,
                    "account_id=? AND event_id=? AND "
                    + "(effective_at IS NULL OR effective_at<>?)",
                    new String[]{accountId, change.eventId(),
                            Long.toString(change.effectiveAt())});
            adjusted |= changed > 0;
        }
        if (adjusted) bumpDeltaRevision(db, accountId);
        db.setTransactionSuccessful();
    } finally {
        db.endTransaction();
    }
}
```

`db.endTransaction()` 在未 setTransactionSuccessful 时回滚，finally 用于正常资源/事务收尾，不是无关异常扫描。Electron 的 applyAck 用现有 withTransaction 执行同样 SQL。ACK 已终结的 outbox 不再发送；本机原始事件没有被这段代码删除，所以仍可参与尚未覆盖的近期调整。

## 5. `BundleService.refresh()` 与 `createRerankSnapshot()`

`BundleService.refresh(context)` 先读取当前账号的授权/epoch 状态，再获取个人推荐包或公共包；收到个人包后核对 accountId、模型、契约、同版字段与有效期。若词表未缓存，`ensureFeatureSpace(version)` 下载原始字节并校验 SHA-256，再解析；失败保持原先完整且仍有效的包，不把新画像与旧词表混用。

`validateBundle(bundle)` 只检查影响计算的契约：ID/版本、候选最多 300 且去重、向量维度/坐标/有限值、画像及向量范数容差、卡片 repoId 对应关系、processedThrough 各流唯一。它不重复检查操作系统每个组件。`installBundle(accountId,bundle,featureSpace)` 在一个 SQLite 事务中写词表、正式画像、候选、水位及 active_bundle_id，递增 bundle_cache_revision。服务端同一 batch 因当前可见性过滤而返回更少候选时，也必须增加该 revision。

`createRerankSnapshot(context,serverBatchId)` 由数据库 worker 执行。一个事务中读当前活动包、context 对应账号、FeatureSpace、允许使用的最近 7 天逐次事件、当前隐藏/本人仓库集合、最近 24 小时已看集合以及相关 revision，取得一次 now 后将全部输入保存到 compute_inputs。服务端基础向量始终读 server_portrait_cache，不读上次 local_rank_snapshots.local_vector_json。

同版事件特征优先从该 catalog+featureSpace 的 repository_vector_cache 取。缓存未命中时把事件关联的本机公开 DTO/文本及 metadata 摘要纳入快照，让 Worker 使用冻结词表投影。投影结果缓存在 `featureSpaceVersion+repoId+metadataHash` 的本机命名空间，不覆盖服务端 catalog 快照的权威向量。

如果 historyEnabled=false，快照的 localEvents 与 recentOpenedRepoIds 都为空；已有云端基础画像是否有效取决于独立的云端设置。开启云端分析不能把此前 deviceSeq=null 的事件自动加入 outbox。公共候选的 baseVector 为空，但已登录本机账号仍可用允许的本机近期事件进行调整；游客只保持公共顺序。

| 数据库函数 | 核心查询/写入 | 输出用途 |
| --- | --- | --- |
| `readActiveBundle(accountId)` | runtime.active_bundle_id关联完整批次与同版画像 | 快照的正式基础 |
| `readRecentEvents(accountId,now)` | 当前账号，未删除，按effectiveAt/occurredAt及localSeq取窗口 | 固定本机增量输入 |
| `readVectorsForEvents(events,versions)` | 精确catalog、featureSpace、repoId键；缺失取本机文本快照 | 避免混用词表 |
| `saveComputeInput(snapshot)` | 写inputId、contextId、versions、snapshot_json | 提交时的可信比较依据 |
| `readRuntimeVersions(accountId)` | delta、bundleCache、hidden、owned、privacy、epoch | 阻止旧计算覆盖新状态 |
| `bumpDeltaRevision(accountId)` | 有效事件、删除、时间修正或本机特征变更时递增 | 使计算快照适时失效 |

`readRecentEvents()` 的时间过滤不能直接排除所有未来 occurredAt：未 ACK 的未来事件在计算时被夹到固定 now，其候选读取要保留这类记录，再由 `selectDeltaEvents()` 统一计算窗口。已收到服务器修正则使用 effectiveAt。

## 6. Worker 的纯函数：从本机事件到最终排序

`shared/recommendation/sparse.js` 实现 `addScaled(sum,vector,weight)`、`normalizeTopK(sum,k)` 和 `dot(a,b)`，与 Hadoop 详解第 3 节同样的坐标/权重排序、L2 和双指针算法。数组累加用 Float64Array(8192)，输出普通 number[]，通过 structured clone 传回；不对服务端基础数组原地修改。

`projector.js` 的 `tokenizeFrozen(text,space)`、`countRepositoryFields(repo,space)`、`projectRepository(repo,space)` 按服务端固定词法、字段权重、IDF 与三个块构造项目向量。`resolveEventVector(event,snapshot)` 先查版本正确的缓存向量，再投影 snapshot 中公开文本；缺少有效特征返回空向量并增加覆盖统计，不调用网络补数据。

下面展开 `adjust.js` 的核心函数。streamKey 使用 JSON 数组编码而非拼一个可能冲突的分隔字符串；localSeq 负责本机稳定累加顺序，不能拿发生时间代替上传身份。

```js
const DAY = 86_400_000
const streamKey = (deviceId, streamEpoch) => JSON.stringify([deviceId, streamEpoch])

export function selectDeltaEvents(snapshot) {
  const marks = new Map(snapshot.processedThrough.map(m => [
    streamKey(m.deviceId, m.streamEpoch), m.processedThroughSeq
  ]))
  return snapshot.localEvents.filter(event => {
    if (event.recordKind !== 'open' || event.deleted) return false
    if (event.accountId !== snapshot.accountId) return false
    const at = Math.min(event.effectiveAt ?? event.occurredAt, snapshot.now)
    if (at <= snapshot.now - 7 * DAY) return false
    if (event.deviceSeq == null) return true
    if (event.analysisEpoch !== snapshot.analysisEpoch) return false
    const covered = marks.get(streamKey(event.deviceId, event.streamEpoch)) ?? 0
    return event.deviceSeq > covered
  }).sort((a, b) => a.localSeq - b.localSeq)
}

export function computeLocalAdjustment(snapshot, resolveVector) {
  const events = selectDeltaEvents(snapshot)
  const sum = new Float64Array(8192)
  let usableEventCount = 0
  for (const event of events) {
    const vector = resolveVector(event, snapshot)
    if (vector.indices.length === 0) continue
    const at = Math.min(event.effectiveAt ?? event.occurredAt, snapshot.now)
    const ageDays = Math.max(0, (snapshot.now - at) / DAY)
    addScaled(sum, vector, 2 ** (-ageDays / 3))
    usableEventCount++
  }
  const delta = normalizeTopK(sum, 512)
  const base = snapshot.baseVector
  let alpha = Math.min(0.25, 0.05 * usableEventCount)
  if (delta.indices.length === 0) alpha = 0
  else if (base.indices.length === 0) alpha = 1
  const mixed = new Float64Array(8192)
  addScaled(mixed, base, 1 - alpha)
  addScaled(mixed, delta, alpha)
  return {
    vector: normalizeTopK(mixed, 512), alpha, usableEventCount,
    ignoredEventCount: events.length - usableEventCount
  }
}
```

这个函数每次从 base+当前 delta 重建结果，所以同一批事件不会因用户刷新十次被累计十遍。alpha 最大 0.25 限制短期偏好影响；空基础而有本机方向时取 1，才能让一个新用户看到基于本机近期行为的顺序。两者都空则向量为空，后面保持公共顺序。

例如把服务端的二维示例基础 `(0.939793,0.341743)` 与五条同日、同方向 `(0,1)` 的未覆盖事件融合，delta 为 `(0,1)`、alpha 为 0.25，归一化前为 `(0.704845,0.506307)`。上传 ACK 到这些事件的序号并不改变该结果；新基础覆盖后再由新的 base 重算。此处是解释性输入，不是实验结果。

`rank-v2.js` 的 `filterCandidates(snapshot)` 剔除本机 hidden、owned、确认非 public/已归档项目，按 repoId 去重；`scoreCandidateV2()` 使用向量兴趣与服务端固定公共分量，缺失分量为 null，不当成已知零。全空用户向量的分支提前返回公共顺序，不能把每个人都打出 0 分然后称为个性化。

```js
export function weightedAvailable(parts) {
  let sum = 0, weight = 0
  for (const part of parts) {
    if (part.value == null) continue
    sum += part.value * part.weight
    weight += part.weight
  }
  return weight > 0 ? sum / weight : 0
}

export function scoreCandidateV2(userVector, candidate, openedRecent) {
  const interest = userVector.indices.length && candidate.vector.indices.length
    ? dot(userVector, candidate.vector) : null
  let score = weightedAvailable([
    { value: interest, weight: 0.85 },
    { value: candidate.qualityScore, weight: 0.10 },
    { value: candidate.freshnessScore, weight: 0.05 }
  ])
  if (openedRecent) score *= 0.70
  return { candidate, score, interest }
}
```

“最近已看降权”与“近期兴趣正向调整”不同，前者可使用已进入服务器画像的最近 24 小时事件，后者只能使用未覆盖事件。最近看过某技术方向，提高相近项目的方向匹配；已看项目本身再降权，减少重复推荐。

`rerankCandidatesV2(scored,limit=100)` 使用 MMR，在分数与已选项相似度之间取平衡。维护 `maxSimilarity`，每选出一个项目，只计算它与所有剩余项目的点积，避免每轮重复扫描全部已选项。最近 9 个已选项目加上新项目组成连续 10 项窗口；同 owner 已有 2 项时先跳过，实在无可选项才放宽。

```js
export function rerankCandidatesV2(scored, limit = 100) {
  const remaining = scored.map(item => ({ ...item, maxSimilarity: 0 }))
  const selected = []
  while (selected.length < limit && remaining.length) {
    const recentOwners = new Map()
    for (const item of selected.slice(-9)) {
      const owner = item.candidate.repository.owner.toLowerCase()
      recentOwners.set(owner, (recentOwners.get(owner) ?? 0) + 1)
    }
    const eligible = remaining.filter(item =>
      (recentOwners.get(item.candidate.repository.owner.toLowerCase()) ?? 0) < 2)
    const pool = eligible.length ? eligible : remaining
    let best = pool[0]
    for (const item of pool.slice(1)) {
      const a = 0.80 * item.score - 0.20 * item.maxSimilarity
      const b = 0.80 * best.score - 0.20 * best.maxSimilarity
      if (a > b || (a === b && compareRepoId(item.candidate.repoId,
                                           best.candidate.repoId) < 0)) best = item
    }
    selected.push(best)
    remaining.splice(remaining.indexOf(best), 1)
    for (const item of remaining) {
      item.maxSimilarity = Math.max(item.maxSimilarity,
        dot(item.candidate.vector, best.candidate.vector))
    }
  }
  return selected
}
```

`compareRepoId(a,b)` 复用无符号 UTF-8 字节比较，与 Hadoop 同分规则相同；`dot()` 对空向量返回 0。候选不足 100 时仍执行完整 MMR，不像当前旧函数直接返回未排序数组。只有基础和增量均为空的明确冷启动分支，才在过滤后按服务端 public position 原顺序取最多 100 条，跳过 MMR/owner 多样性调整，保持“公共顺序”的含义一致。

`buildReasonsV2(profile,candidate,adjustment,evidence)` 先保留服务器长期匹配依据；若本机可用事件中存在与该候选同版坐标相交的证据，可补一条“已结合本机近期浏览调整”。具体技术词必须来自实际 topic 或词表贡献，不能仅因为 alpha>0 就给每条候选编相同技术理由。默认最多两条，项目证据都属于当前用户。

`computeRerank(snapshot)` 依次执行 select/resolve/adjust/filter/score/rerank/reasons，输出 inputId、contextId、accountId、inputVersions、localVector、alpha、coverage 和 positions 从 1 开始的 items。每条 item 保留原 candidate.repository 完整 DTO，不能重犯当前 extractRepositoryFeatures 丢失 repoId/fullName 后拿特征对象直接展示的问题。

## 7. 异步计算返回时，怎样知道它还有效

当前 `services/recommendation.js` 的 runWorkerJob 使用桥的可变当前 contextId，新版改为显式传入 snapshot.contextId 和 snapshot.now。`runWorkerJob(snapshot,signal)` 建 jobId→Promise 映射，发送完整请求；`handleWorkerMessage(message)` 按 jobId 取出任务、校验 inputId，成功时 resolve(message.result)，失败时 reject 业务错误，不把外层通信信封当算法结果；`cancelContext(contextId)` 拒绝该上下文全部 pendingJobs，终止或忽略旧 Worker 结果。

Worker 的 `onmessage` 只接 `purpose=rerank_v2`、`modelVersion=mr-content-v2`，调用 computeRerank，返回 `{jobId,inputId,contextId,purpose,modelVersion,result}`。未知 purpose 返回明确协议错误；不以默认 profile 分支继续训练正式画像。真正运行错误通过结构化结果或 onerror 完成 Promise，不能只 console.error 而让页面永久 loading。

```js
export async function computeAndCommitRerank(snapshot, capturedInvoke) {
  const result = await runWorkerJob(snapshot)
  const committed = await capturedInvoke('recommendation.commit', {
    purpose: 'rerank_v2', inputId: snapshot.inputId, result
  })
  if (!committed.ok) {
    const error = new Error(committed.error.message)
    error.code = committed.error.code
    throw error
  }
  return committed.data
}
```

`capturedInvoke` 在本次动作开始时用 `nativeBridge.capture()` 创建，不能在 Worker 返回后重新 capture 成用户 B 的上下文，再把用户 A 的结果提交。原生 `commitLocalRanking(context,result)` 仍是最终防线：在事务内读取 compute_inputs.inputId 的保存值，而不是相信 result.inputVersions 自报正确。

```text
commitLocalRanking(context,result) 的事务顺序：
读取 compute_inputs，确认 inputId 属于 accountId、contextId；已消费则返回原回执
读取当前 runtime、active bundle 与各revision，逐项比较保存的输入版本
确认当前包仍有效、隐私未停用、返回repoId均在输入候选集合且无重复
分配clientBatchId，保存local_rank_snapshots与每条固定position
将该inputId标记consumed，将pending_client_batch_id指向新批次
提交后返回clientBatchId、serverBatchId、generatedAt、coverage
```

这是算法步骤，不是伪造的 SQL 存储过程。`matchesSavedVersions(saved,current)` 明确比较 accountId、contextId、serverBatchId、generationId、featureSpaceVersion、catalogSnapshotId、privacyRevision、analysisEpoch、deltaRevision、bundleCacheRevision、preferenceRevision、hiddenRevision、ownedRevision；任一不同抛 INPUT_CHANGED。若同 inputId 已成功提交，返回原 clientBatchId 作为幂等重试，不再插入另一批；此时也不把它重新设成最新 pending。

`refreshAndCompute()` 遇 INPUT_CHANGED 允许合并重新创建一次快照；第二次仍变化则保留当前展示并等待下一次事件/刷新，不循环无限重算。成功只表明本机排序已保存，正式基础画像依旧在 server_portrait_cache，不被覆盖。

## 8. 页面和 Pinia 应调用哪些函数

`stores/feed.js.refreshRecommendations({activate})` 是新的业务入口，顺序为 capture 当前上下文、cloud.refreshBundle、createSnapshot(rerank_v2)、computeAndCommitRerank、必要时 activateBatch、读取第一页。旧的 computeAndCommitProfile→planDiscoveryQueries→refreshPersonalizedCandidates 链路退出该函数。服务端尚未就绪时用明确标识的公共候选入口，并显示画像整理中。

store 增加 `visibleClientBatchId`、`pendingClientBatchId`、`afterPosition`、`generationId`、`sourceMode`、`hasPendingUpdate`。`activateBatch(id)` 先由原生确认该批属于当前账号且未失效，在事务中切 visible 指针，再清当前页数组并从 position 0 读第一页。初次进入或用户点击刷新可以激活；后台新增浏览只生成 pending，正在阅读时保留 visible。

`loadMoreRecommendations()` 固定读取 visibleClientBatchId，传 afterPosition 和 limit=20。底层 SQL 按原 position 游标查询，并过滤当前隐藏记录：

```sql
SELECT i.position, i.repo_id, i.repository_json, i.reasons_json, i.score
FROM local_rank_items i
JOIN local_rank_snapshots b ON b.client_batch_id = i.client_batch_id
WHERE b.account_id = :accountId
  AND b.client_batch_id = :clientBatchId
  AND i.position > :afterPosition
  AND NOT EXISTS (
    SELECT 1 FROM recommendation_feedback f
    WHERE f.account_id = b.account_id AND f.repo_id = i.repo_id AND f.hidden = 1
  )
ORDER BY i.position
LIMIT :limitPlusOne;
```

取 21 项，展示前 20 项；存在第 21 项才返回 nextPosition，值为本页最后一个已展示项目的原 position。没有下一页则 null。隐藏第 3 项后不会按新的数组长度改变位置，后续页也不会漏项。隐藏之外的当前公开性/归档门禁在读取前应用同样过滤；不能只在 Worker 开始时过滤一次。

`hideRecommendation(repoId)` 先原生写本机隐藏与 mutation outbox、递增 hiddenRevision/deltaRevision，再从当前数组移除；联网后上传同一 mutationId，云端最终回执更新 feedbackRevision。`MutationSync.flush()` 按当前账号发送待确认设置/反馈：409 时拉权威设置并呈现冲突，不用旧 revision 覆盖新值；关闭分析意图在离线时立即本机生效，恢复网络后优先发撤回再发任何浏览日志。

`stores/portrait.js.loadForGeneration(generationId)` 并行读取当前用户的 portrait 与同版 cohort summary，响应回到对应捕获的 contextId 才写 store。202 显示整理中，真实小群体 suppressed 显示样本不足，synthetic 明确显示合成实验数据。另一版本群体尚未就绪时不拼接旧群体报告到新个人面板。

`PortraitPanel.vue` 的 `toLanguageRows(profile)` 仅把已归一化分布转成显示百分比；`toInterestRows(profile)` 给出前 8 个真实兴趣及可展开 evidenceRepos；`openEvidence(repoId)` 通过已有项目详情与打开服务执行，不读取其他用户资料。百分比格式化只影响显示，不把舍入后的数传回算法。

`CohortPanel.vue` 的 `toGroupRows(summary)` 使用 memberCount 和 validCounts 解释覆盖分母；`selectGroup(cohortId)` 只切换已有聚合内容，不向服务端请求任意成员列表。`SettingsModal.vue.onCloudConsentChanged(value)` 区分本机历史开关与云端分析，默认迁移为关闭云端；`requestCloudClear()` 说明范围后调用原生隐私操作，收到新的 epoch 后清理旧调整输入。

保留 App.vue 外框、底部导航、TrendingView 项目卡片、ProfileView 资料区与历史/Star/本人仓库三个页签。画像和群体面板放在原技术兴趣区域内，不新增一套后台首页。同步状态用“已上传、等待画像更新”等可理解语言，不把 HDFS 路径、JAR 名或8192维数组放入普通用户流程。

## 9. SQLite v3 迁移和缓存回收

Electron `migrateV2ToV3()` 与 Android `HappyGitDbHelper.onUpgrade()` 使用同一逻辑 schema。先可靠备份现有库；开启一个迁移事务创建云端状态、逐次事件、outbox、词表/向量/包缓存、compute_inputs、runtime 和本机排序表；初始化 cloud_sync_enabled=0；保留账号、真实历史和 last_counted_at；提交后更新 user_version=3。失败回滚，不删除旧库重建。

`local_activity_events` 额外存 device_id、analysis_epoch、local_seq、record_kind、deleted 标记及原始公开数据引用；`client_account_runtime` 增加 next_local_seq，cloud/state 和 local_sync_state 分别保存授权与设备序列。历史原记录无法还原逐次打开，迁移不生成 eventId，不把旧 content-v1 缓存改个版本号冒充 Hadoop 画像。

`pruneLocalCache(accountId,now)` 保留当前 visible、pending 及其依赖的服务端包/词表；回收无引用旧批次和已消费 compute_inputs。逐次事件在已被正式画像覆盖且超过 7 天窗口后可提前回收；尚未确认上传的正文依据保留策略先转换 discard，不能被聚合历史“最多5000行”清理顺带删掉。向量缓存按版本和 metadataHash 回收，不只按 repoId 保留一份。

退出/换号的 `resetForContextChange()` 清 Pinia、取消 Worker/网络上下文、暂停对应上传；本地表仍按 account_id 分区保留。`readPortrait`、`listLocalRanking`、`readComputeInput` 均带账号谓词，即使一个错误客户端拿到了另一人的 batchId，也不能通过本机领域接口读取其内容。

## 10. 学习与落地顺序

先实现 sparse/projector/adjust/rank-v2 的纯函数，就能用固定输入理解推荐如何改变；再写 SQLite v3 与 recordBrowse/outbox，使输入可信；随后完成双端 HTTP、候选包和快照提交；最后替换 feed 调用链并接入两个画像面板。每一步都有明确上游与下游，不需要先重写全部页面。

合入 develop 后集中验证：30 秒内重复打开只一条有效事件；ACK 到 105 而画像到 100 时增量仍在；G2 切换后同样五条不再重复加入；隐藏不会漏分页；换号期间旧 Worker 不能提交；两端同制品投影在容差内一致；离线只使用仍有效或明确标时的缓存。真实 Electron/Android 登录与原生数据库必须在对应平台验证，普通浏览器预览不能代替。

本篇交付的是可沿函数实现的客户端设计，尚未改造 Vue、Electron、Android 或运行任何客户端测试。实现和后续验收记录应分开保存，避免把文档中的例子当成已经完成的功能。
