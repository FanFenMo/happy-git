# 新 HappyGit 第一版服务端详细设计

版本 1.0，2026-10-29；设计基线、阅读顺序见[总览](README.md)。本篇把在线请求、数据采集、日志归档、批处理编排与结果发布落实到函数。批量算法的 Mapper、Reducer、Driver 在 [Hadoop 计算实现详解](Hadoop计算实现详解.md)继续展开，参数字段统一使用[接口与数据契约](接口与数据契约.md)。所有拟新增函数均未实现。

## 1. 工程边界与代码落点

现有 `server/src/main/java/com/happygit/server` 只有 OAuth、热门项目等基础入口。保留 `HappyGitApplication` 和现有部署外壳；新增 JDBC 持久化和版本迁移，在线服务使用 `NamedParameterJdbcTemplate` 编写明确 SQL。这里选择 JDBC 是为了让“锁哪一行、何时提交”直接可读，不再引入一套难以从设计看出查询行为的 ORM。

```text
server/src/main/java/com/happygit/server/
  auth/       AppAuthenticationFilter, OAuthLoginService, AppSessionService
  account/    AccountController, AccountService, PreferenceService, PrivacyService
  ingest/     EventController, EventIngestionService, EventCanonicalizer
  query/      RecommendationController, BundleQueryService, PortraitQueryService
              CohortQueryService, ProjectQueryService, FeatureSpaceQueryService
  repository/ UserRepository, SessionRepository, EventRepository, StreamRepository
              PublicationRepository, BundleRepository, MutationRepository
  model/      api、领域DTO；使用已约定的标识和版本
server/src/main/resources/db/migration/
              V1__cloud_identity.sql、V2__ingestion.sql、V3__publication.sql

collector/src/main/java/com/happygit/collector/             拟新增，JDK 11
  github/     GitHubPublicClient, CrawlTaskRunner, CollectionCollector
  archive/    EventArchiver, ArchiveRepository, ImmutableHdfsWriter
  pipeline/   InputManifestBuilder, PipelineCoordinator, JobAttemptRepository
  publish/    ResultValidator, ResultImporter, ResultPublisher
  privacy/    PartitionRewriteService

mapreduce/src/main/java/com/happygit/hadoop/               拟新增，独立作业JAR
  model/、io/、math/、text/、jobs/、driver/
```

Controller 把 HTTP 参数转换为领域参数；Service 决定业务步骤和事务；Repository 只执行固定 SQL；DTO 只承载数据。以接入为例，Controller 不循环插入日志，Repository 不判断画像权重，Service 不拼接任意用户提供的表名。这样读一个函数时可以明确它负责哪一层。

MySQL 迁移按身份、接入、发布三组执行；collector 使用相同 schema，但仅操作其职责内的表。HDFS 客户端只进入 collector/mapreduce 的 JDK 11 进程，Spring Boot 请求线程不加载 Hadoop 运行环境。后台循环通过持久任务和租约恢复，首版不增加消息中间件。

## 2. 登录：把 GitHub 身份转换为本服务会话

现有 OAuth 代码可参考 URL 构造和 HTTP 交换，但新接口不能继续把 GitHub token 交给前端。拟新增 `auth/OAuthLoginService.java` 的业务方法如下。每个方法只返回表中领域值，Controller 统一包装 requestId。

| 函数签名 | 调用者、输入与输出 | 内部实现及状态变化 |
| --- | --- | --- |
| `LoginChallenge begin(DeviceDescriptor device)` | `POST /auth/github/begin`；返回 challengeId、authorizationUrl、pollProof、pollIntervalMs | 生成 32 字节随机 state、pollProof、PKCE verifier；存 state/proof 摘要及加密 verifier、设备描述、10 分钟期限；URL 使用 S256 challenge |
| `LoginCompletion complete(String state, String code)` | GitHub callback；返回完成页状态 | 用 state 摘要领取 challenge 的交换租约；事务外换上游 token，调用 `/user`，取得数字 ID；事务内登记 verified identity，状态变为 ready；清临时 token/verifier |
| `PollResult poll(String challengeId, String pollProof)` | 原生登录任务定时调用 | 核对 proof 摘要；pending 返回等待；ready 时行锁内创建应用会话并将 challenge 改为 consumed，一次返回应用 token；过期/已领取返回明确状态 |
| `void cancel(String challengeId, String pollProof)` | 原生取消登录 | 核对证明后将未消费任务置 cancelled，后到的 callback 不得创建可领取会话 |

GitHub 文档已定义 state、S256 PKCE 和授权码交换参数；本设计额外加入的是应用原生端领取会话的 challenge/proof 机制。[GitHub OAuth 官方说明](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/authorizing-oauth-apps)

`oauth_challenges` 的主键为 challenge_id，state_hash 和 poll_proof_hash 唯一；字段包括 encrypted_verifier、device_id、platform、state、expires_at、exchange_lease_until、verified_github_id、verified_profile_json、consumed_at。state 取 pending/exchanging/ready/consumed/cancelled/failed。交换时不持有数据库锁等待 GitHub；租约防止同一 callback 并发换码。领取完成后网络响应丢失时首版重新发起登录，不把明文 token 长期保存在挑战表以便重放。

`AppSessionService.create(userId,deviceId)` 生成独立随机 access/refresh token，只存 SHA-256 摘要。access 有效 15 分钟，refresh 有效 30 天。`refresh(refreshToken)` 锁定对应 session，确认未撤销后轮换两个摘要和期限，旧 refresh 失效；`logout(principal)` 设置 revoked_at。HTTP 客户端同一 session 只并发执行一次 refresh；刷新响应丢失且旧凭据已失效时回到登录流程，不无限重试旧 refresh。

`AppAuthenticationFilter.authenticate(request)` 读取 Bearer access token，哈希查有效会话，建立只含 userId、accountId、deviceId、sessionId 的 `AuthPrincipal`。查到过期返回 401；查到撤销同样拒绝。`GET /me/*` 的 userId 都取这个 principal，不能从查询参数 accountId 替换。会话摘要比对只用于当前认证边界，不为每次请求扫描整张用户表。

登录只完成身份确认；`DeviceService.register(principal, requestedStreamEpoch, expectedAnalysisEpoch)` 再在用户锁内幂等创建 devices/device_streams，默认 next seq=1，核对当前 epoch。若客户端恢复了已有流则返回权威水位；用户重置分析后只能注册新流。用户可以登录但不开启云端分析，此时仍可以读公共候选。

## 3. 接收日志：一个事务完成事件和 ACK

拟新增 `ingest/EventController.java` 中的 `accept(principal,batch)` 绑定 `POST /api/v2/me/events:batch`。它先限制请求体大小、条数和连续序号结构，然后调用 `EventIngestionService.acceptBatch()`。一次调用最多处理 500 条，校验失败整批不写；因此客户端不需要猜测半批哪几条成功。

`EventCanonicalizer.hashOpen(event)` 按契约中的固定字段数组产生 UTF-8 字节并取 SHA-256；`validateBatchShape(batch)` 检查非空、首序号、每条连续、批头与 open 一致、ID/时间可表达以及摘要格式。`validateOpen(event)` 校验 repoId 和允许的 source，返回计算好的摘要；不要求当时项目已经被爬取，否则刚发现的新项目会阻塞整个设备流。

下面是核心实现，使用 Java 17 的 record 表达结果。`BusinessException` 为统一 HTTP 业务错误，抛出时事务回滚。Spring 事务方法由 Controller 经注入的 Service 调用，不在同类中绕过代理自调用。事务代理边界可参照 [Spring 事务注解说明](https://docs.spring.io/spring-framework/reference/data-access/transaction/declarative/annotations.html)。

```java
@Transactional
public IngestAck acceptBatch(AuthPrincipal principal, EventBatch batch) {
    validator.validateBatchShape(batch);
    UserState user = users.lock(principal.userId());
    user.requireCloudEnabledAt(batch.analysisEpoch());
    StreamState stream = streams.lock(principal.userId(),
            principal.deviceId(), batch.streamEpoch());
    stream.requireOpenAt(batch.analysisEpoch());

    long accepted = stream.acceptedThroughSeq();
    long receivedAt = clock.millis();
    List<TimeAdjustment> adjustments = new ArrayList<>();
    for (EventRecord record : batch.events()) {
        if (record.isOpen()) validator.validateOpen(record);
        if (record.deviceSeq() <= accepted) {
            EventReceipt old = events.findReceipt(stream.key(), record.deviceSeq());
            if (old == null) throw new BusinessException("SYNC_WINDOW_EXPIRED");
            old.requireSameIdentityAndHash(record.eventId(), record.payloadHash());
            if (old.timeAdjusted()) adjustments.add(old.toAdjustment());
            continue;
        }
        if (record.deviceSeq() != accepted + 1) {
            throw BusinessException.sequenceGap(accepted + 1);
        }
        EventReceipt receipt = record.isOpen()
                ? EventReceipt.open(stream.key(), record, receivedAt)
                : EventReceipt.discard(stream.key(), record, receivedAt);
        events.insert(receipt); // 唯一索引冲突转换为409，整个事务回滚
        accepted = record.deviceSeq();
        if (receipt.timeAdjusted()) adjustments.add(receipt.toAdjustment());
    }
    streams.setAcceptedThrough(stream.key(), accepted);
    return new IngestAck(principal.deviceId(), batch.streamEpoch(), accepted,
            stream.exportedThroughSeq(), receivedAt, adjustments);
}
```

`users.lock(id)` 使用主键 `SELECT ... FOR UPDATE`，同时阻止接入与该用户的隐私重置交叉提交；`streams.lock(key)` 锁一条设备流；所有接入都按用户后设备流的顺序取锁。SQL 行锁在事务提交时释放，其作用与使用边界见 [MySQL 锁定读](https://dev.mysql.com/doc/refman/8.4/en/innodb-locking-reads.html)。课程规模先用用户排他锁，代价是同用户多设备串行接入；后续有实测瓶颈再优化。

`EventReceipt.open()` 保留 occurredAt，计算 effectiveAt 和 timeAdjusted，存正文及摘要；`discard()` 只保存序号、eventId、原摘要与终结状态。`requireSameIdentityAndHash()` 对同 seq 比较 eventId 和 hash，recordKind 不要求相同：已接收 open 后到 discard 只确认旧接收，已接收 discard 后到 open 也只确认终结，不恢复正文。若同 eventId 出现在另一 seq/流，数据库 `(user_id,event_id)` 唯一约束拒绝。

`events.findReceipt(key,seq)` 即使正文已归档清理仍能返回身份和时间修正。上例的 `accepted` 是连续边界；重复 101—105 时，若服务端已经收到 110，会核对旧记录并返回 110，而非把水位倒退到 105。序号缺口返回 expectedSeq。客户端必须查询权威状态修复接续，不能把缺失 seq 随便跳过。

事务提交成功才由 Controller 写 HTTP 响应。服务器在提交后、回应前断开时，客户端重试同一 payload 不增加记录。这是幂等接收的核心，比“请求只发一次”的假设可靠。

## 4. 设置、反馈与隐私如何进入下一轮输入

`AccountService.read(principal)` 查询 app_users、当前 preferences 与完整集合状态，返回 accountId、公开资料、cloudSyncEnabled、analysisEpoch、privacyRevision、preferenceRevision、feedbackRevision。`AccountService.listRepositories(principal,kind,cursor,limit)` 首次固定 active collectionId，后续 cursor 绑定 collectionId 和最后 sortKey/repoId；若集合已回收返回游标失效，不把后一页切到新集合。

`PreferenceService.update(principal,command)` 的 command 含 mutationId、expectedRevision、expectedPrivacyRevision、manualTags、cloudSyncEnabled。先查 `account_mutations(user_id,mutation_id)`；同摘要重试返回原结果，不同摘要冲突。手动标签去重、规范化并保存原文与规范 token；词表外标签可展示，不捏造向量坐标。revision 使用 `UPDATE ... WHERE preference_revision=:expected`，受影响行数不为 1 返回 409。

如果命令改变云端分析授权，则由 `PrivacyService.changeConsent()` 接管同一事务，增加 privacyRevision；关闭分析立即停止后续接入、屏蔽该用户个人结果，并使涉及该用户的群体结果失效。重新开启需要客户端先读取当前 revision 并显式提交，不能用旧离线开关悄悄恢复授权。重新启用后创建新流，旧积压正文不补传。

`PreferenceService.update()` 统一先锁 real 发布通道、再锁当前用户，然后检查并应用 revision；即使本次只修改手动标签也遵循这个短事务顺序。不能先锁用户，再因发现授权变化而补锁发布通道，否则会与发布器形成反向锁序。网络请求不放在这个事务中。

`FeedbackService.setHidden(principal,repoId,hidden,mutationId)` 在用户锁内检查 mutationId，UPSERT `user_repo_feedback`、递增 feedbackRevision，保存回执。当前候选读取立即过滤隐藏项目，下一轮 Manifest 捕获隐藏集合，使其不再贡献正向兴趣。解除隐藏同样使用显式 hidden=false，不用 toggle；重试 toggle 会改变两次状态，setHidden 不会。

`PrivacyService.request(principal,kind,mutationId)` 支持 clear_cloud_browse/delete_cloud_account。它在事务中先锁 publication_channels 的 real 通道，再锁用户；增加 privacyRevision，clear_cloud_browse 还增加 analysisEpoch，关闭旧设备流，写 privacy_requests 和 analysis_tombstones。该事务标记旧 generation 的群体结果不可读。collector 发布也遵守“发布通道→用户按 ID 顺序”的锁顺序，避免撤回和发布互相越过。

`PrivacyService.readStatus(principal,requestId)` 只查询本人的请求，分别返回 logicalBlocked、recomputed、purged。`PartitionRewriteService.rewrite(requestId)` 在后台读取受影响分区，过滤已撤回的 subject/epoch，写新文件、关闭、校验记录数与摘要，在受控 Manifest 中替换引用；引用切换后清旧文件，备份到期再记录其清理进度。这里是具体的数据生命周期，不尝试对每条日志创建独立 HDFS 文件。

本机清空与以上接口不同。本机 discard 只表示不再发送某条待上传正文，不撤回已经接收的云端 open。界面文案、函数命名和数据状态都保持这一区别。

## 5. 在线读取：把 Hadoop 结果稳定地交给客户端

`BundleQueryService.readForUser(principal)` 在一个 REPEATABLE READ 只读事务中固定 active generation，再读取同版 user_portraits、portrait_watermarks、recommendation_batches/items 和 repository_vectors。读取用户当前 privacyRevision/analysisEpoch，不匹配则返回 pending 或云端停用，不返回旧个人结果；查询中新隐藏/不公开/归档项目立即从 candidates 排除。返回值为契约定义的完整 RecommendationBundle。

读取时不执行 J09，也不在 API 中临时调用旧画像算法。若没有已发布结果，Controller 返回 HTTP 202，data 为 `{state:"pending",retryAfterMs:60000,publicAvailable:true}`；已有结果但过期则返回明确 stale 状态及公共入口，不把 expiresAt 延长。收到合法旧 generation 的客户端可按其实际时间展示缓存，但不能标成新的计算结果。

`PortraitQueryService.read(principal,generationId)` 读取指定发布版本中本账号画像，执行与 bundle 相同的隐私门禁；`CohortQueryService.read(generationId,channel)` 校验 generation 属于对应数据通道且 cohort_invalidated_at 为空，返回聚合报告。真实群体小于 10 人时只返回 cohortId 与 suppressed=true，不下发其分布或成员信息。首版无任意用户筛选接口。

`ProjectQueryService.detail(repoId)` 读取已采集的公开详情；缺失时以 kind+target 唯一任务键加入采集队列并返回 pending；不让请求线程抓 README 等待全套处理。当前可见性优先于历史展示缓存。`ProjectQueryService.popular(channel)` 读取 J12 公共包，不带任何个人数据。

`FeatureSpaceQueryService.read(version,ifNoneMatch)` 仅从 feature_spaces 注册表查已发布制品，匹配 ETag 则 304；否则返回已镜像到 API 静态制品目录的原始字节及摘要。API 不接受任意 HDFS 路径；collector 导入时同时完成镜像。这样 API 进程不需要为了一个下载接口加载 Hadoop 依赖。

`SyncQueryService.read(principal)` 返回当前设备所有仍需接续流的 accepted/exported 水位，加上当前合法 generation 中对应 processed 水位、analysisEpoch 和 privacyRevision。它不能把 accepted 值直接复制到 processed 字段。

## 6. 公开数据采集：先收集事实，再交给 MapReduce

拟新增 `collector/github/GitHubPublicClient.java` 使用 JDK 11 HttpClient。`fetchPage(uri,etag)` 只接受配置允许的 GitHub API host 和固定路由，发送条件请求，返回 `FetchedPage(status,body,nextLink,etag,retryAt)`；不把令牌写入 body 或日志。`computeRetryAt(headers,now)` 优先使用 Retry-After，其次剩余额度为零时的 reset 时间；其他限流使用有上限的指数退避，401/权限不足不当作普通网络重试。

`normalizeRepository(json,fetchedAt)` 将 REST 的 snake_case 转为现有 camelCase DTO，数字 ID 从 JSON 原始整数文本转为字符串；未知计数为 null，公开性明确才标 public。`fetchReadme(repo)` 读取该公开仓库 README 并转换为固定纯文本输入，不执行 HTML 或脚本。`readPublicEvents(account)` 记录本轮实际观测时间范围和分页信息，不将可见事件当成完整历史。

`CrawlTaskRunner.claim(now)` 在短事务中领取一条到期任务，更新 leaseOwner/leaseUntil；`run(task)` 按类型分发 repository、owned、stars、events；`completePage(task,batch)` 只有在 HDFS 文件提交后才保存新游标；`defer(task,retryAt)` 释放租约并记录下一次可运行时间。课程部署使用单个全局采集预算，避免多个 worker 各自按同一 token 的额度独立请求。[GitHub REST 最佳实践](https://docs.github.com/en/rest/using-the-rest-api/best-practices-for-using-the-rest-api)

`CollectionCollector.collectPage(task)` 为本次 collectionGeneration 写 staging 成员和原始批次，保存 nextLink；`activateIfComplete(task)` 只在分页结束且所有页文件提交后将 collection_snapshots 标 complete，再切换用户 kind 的 active collectionId。分页中断只留下 staging，读取与 J07 继续使用旧完整集合。若此前从未有完整集合，UserSeed 的 starsComplete/ownedComplete 为 false，不把缺失当空集合证明。

一个具体顺序是 `claim → fetchPage → normalize → ImmutableHdfsWriter.writeBatch → completePage → activateIfComplete`。collectPage 的 batchId 由 taskId、collectionGeneration、page ordinal 固定派生，重试同页复用该 ID。HDFS 写成功而 MySQL 游标没更新时，下一次先查该批次登记与文件摘要，不能生成另一个逻辑页后直接跳到下一页。

公共仓库重命名以 repoId 合并并更新 repository_aliases；返回不可公开状态时立即更新在线 repositories 的展示门禁，并在下一 J01 快照中排除。GitHub 数据覆盖与新鲜度仍受实际采集时间限制，接口不承诺扫描全站。

## 7. 归档和调度：怎样让批处理输入可重放

`EventArchiver.archiveNext()` 不把 MySQL 与 HDFS 假装成一个事务。它通过三个可恢复步骤推进：先保留范围，再写不可变文件，最后提交登记。流程内的每个函数都能通过 archiveBatchId 找到同一逻辑工作。

`ArchiveRepository.reserveRanges(limitBytes,now)` 在短事务中领取流的 `[exported+1,accepted]` 连续区间，创建 archive_batches=prepared 和 archive_batch_streams。每流最多一个未完成预留，防止两个归档器抢同一前缀；批次可含多个用户流，避免一人一小文件。`readReserved(batchId)` 只按预留范围与主键顺序读取，先固定行集合再序列化，不能把后来插入的行悄悄追加。

`ImmutableHdfsWriter.writeBatch(batchId,records)` 使用配置根目录、同一命名空间的 `.inprogress` 路径，流式写 UTF-8 JSONL，同时累计记录数、字节数、SHA-256；关闭流后提交为正式路径。已存在正式路径时读注册信息并校验摘要，不能无条件覆盖。正文、最小 discard 回执和时间修正一并归档。

`ArchiveRepository.commit(batchId,fileDescriptor)` 锁批次和各流，确认文件完整且区间紧接旧 exported 水位，将批次置 committed、登记 manifest 文件，并推进 exportedThroughSeq。崩溃恢复时 `resumePrepared()` 优先处理已有 prepared 批次：只有临时文件则重写；已有正式文件则核对并补提交；已 committed 则直接返回原回执。未归档正文不被保留期任务清理。

`InputManifestBuilder.freeze(channel,referenceTime)` 在数据库一致快照内读取已提交的输入注册表、当前完整集合、隐私及偏好、目标用户种子和流边界。复制这些控制数据为不可变 HDFS 文件，得到各自摘要；再生成 Manifest 和 runId。Manifest 只列确切文件，不保存一个未来可能增加文件的通配目录。HDFS 处理模式与吞吐型存储边界见[原 Hadoop SDD](../../sdd/HadoopSDD.md)。

小时批次复用最近成功的 catalog 与 FeatureSpace 时，必须验证其 catalogSnapshotId、算法和输入摘要相匹配；每日新语料批次运行 J01—J06。调度默认北京时间 03:00 冻结公共语料，每小时运行画像链，但这些只是部署配置，本次不创建系统定时任务。

`PipelineCoordinator.claimRun()` 从 queued 任务取得带 fencingToken 的租约；`runNextStage(runId)` 根据固定 DAG 找所有依赖完成的 stage；`submitStage(stage)` 用固定 JobFactory 和 Manifest 创建 Job，先持久化 attemptId 与唯一 jobName，再 submit；`reconcileAttempt()` 读取已记录的 JobID/ApplicationID，等待已存在任务，不直接重复提交。若提交响应丢失而尚无 ID，按唯一 jobName/attemptTag 在 YARN 查询；在上一次提交结果尚不能确定时不创建下一 attempt。

`finishStage(attempt)` 记录 Hadoop 状态、实际 Counters、输出路径和摘要；成功才允许下游；失败将 run 置 failed，旧在线 generation 不变。`cancelRun(runId)` 取消已知 JobID，停止后续提交，不删除已发布结果。后台恢复和取消都按确切任务身份操作，不扫机器上的所有 Java 进程。

运行状态为 `queued → running → validating → publishing → published`，失败/主动取消分别为 failed/cancelled。所有输出使用 `runId/stage/attemptId` 独立目录；失败重试换 attemptId，输入 Manifest 不变。Task attempt 的自动重试由 Hadoop 承担，应用层不在 Mapper 里增加另一套 HTTP/SQL 重试。

## 8. 发布：成功的作业怎样变成可读结果

`ResultValidator.validate(manifest)` 核对每个成功 stage 的 `_SUCCESS`、实际文件摘要、schema、维度、同版 FeatureSpace、用户/项目引用、候选唯一且不超过 300、用户种子与画像数量、各作业自己的计数守恒，以及新增事件序号范围的终结记录。`_SUCCESS` 只是输出提交标记，单有这个文件不能证明业务计数正确。

`ResultImporter.importGeneration(result)` 幂等写入 staging generation，按主键批量导入 repository_vectors、user_portraits、portrait_watermarks、recommendation_batches/items、cohort_portraits 和公共排名表。每个导入分片记录 digest 和 rowCount；同分片重试相同内容复用，内容不同拒绝。它可以分块提交，原因是 staging 尚不可见，不必为整批导入持有长事务。

`ResultPublisher.publish(generationId)` 是最终短事务，内部调用如下。`importer.assertComplete` 只读导入登记及数量，实际大文件核对已在前一步完成。

```java
public void publish(String generationId) {
    String channelName = generations.readChannel(generationId);
    transaction.executeWithoutResult(status -> {
        PublicationChannel channel = publications.lock(channelName);
        Generation g = generations.lock(generationId);
        if (g.isPublished()) return; // 重试不把较旧一代重新切成active
        g.requireStaging();
        importer.assertComplete(g.id());
        List<UserState> current = users.lockInIdOrder(g.subjectIds());
        publicationRules.requireSamePrivacyAndEpoch(g, current);
        publicationRules.requireNotExpired(g, clock.millis());
        publicationRules.requireNonRegressingWatermarks(g, channel.activeGenerationId());
        generations.markPublished(g.id());
        publications.setActive(channel.name(), g.id());
    });
}
```

锁顺序统一为 publication channel → generation → users；channel 归属在创建 generation 后不可修改，所以先只读取得 channelName，再按上述顺序加锁。`readChannel()` 只返回已登记 generation 的通道，不能由 HTTP 参数覆盖。

`requireSamePrivacyAndEpoch` 比较 Manifest 冻结的 privacyRevision/analysisEpoch 与当前授权状态；不一致时整代不可发布，不能只删几个人选项却保留污染的群体平均值。普通手动兴趣或隐藏 revision 变化允许该代作为旧快照发布，包内保留原 revision，在线读取仍应用当前隐藏集合，并把更新需求合并到下一批次。隐私变动不使用这项宽容。

`requireNonRegressingWatermarks` 比较同一仍有效设备流，防止较慢的旧 run 覆盖较新的已发布处理前缀；generation 的 referenceTime 也不允许倒退。校验失败保留 staging 便于定位，active 指针保持不变。发布事务提交后，API 才能查询该 generation。

真实数据和 synthetic 数据使用独立 channel、subject namespace、HDFS 根目录与发布指针。实验账号无法通过生产 `/me` 被读取。演示入口只读实验通道并明确展示来源，不触发真实 GitHub Star 或登录。

## 9. Repository 函数需要怎样写 SQL

这些函数不各自制造业务事务，事务由上面的 Service 或 collector 单元持有。除明确的批量流式读取外，都依靠已定义主键或索引，避免在线读取扫描所有历史日志。

| 文件与函数 | SQL 的核心条件 | 返回给调用者的内容 |
| --- | --- | --- |
| `UserRepository.lock(userId)` | app_users 主键，FOR UPDATE | 授权、epoch、revision |
| `StreamRepository.lock(userId,deviceId,epoch)` | device_streams 复合主键，FOR UPDATE | 接收/导出边界和流状态 |
| `EventRepository.findReceipt(key,seq)` | ingest_events 完整主键 | 原 eventId/hash、终结状态、时间修正 |
| `EventRepository.insert(receipt)` | INSERT，保留唯一约束 | 插入完成；重复冲突由 Service 处理 |
| `StreamRepository.setAcceptedThrough(key,seq)` | 持有行锁后 UPDATE 对应流 | 更新行数必须为1 |
| `MutationRepository.find/save(user,mutationId)` | account_mutations 复合主键 | 请求摘要、已提交结果 revision |
| `PublicationRepository.lock(channel)` | publication_channels 主键，FOR UPDATE | 当前 generation |
| `BundleRepository.read(generation,user)` | 先取批次再按 position JOIN 同版向量 | 完整画像、候选、水位 |
| `CollectionRepository.readPage(collection,cursor,limit)` | 固定 collectionId，复合排序键大于游标 | 同一完整集合的后续成员 |
| `ArchiveRepository.readReserved(batchId)` | 批次子表中的连续主键范围 | 流式事件，不全量载入 JVM |

在线读取完整包的向量关联条件必须同时含 catalog_snapshot_id、feature_space_version、repo_id。只按 repoId JOIN 会把新词表向量混进旧画像。个人画像和候选都按 generation_id＋user_id 查，客户端提交一个他人的 batchId 不会绕过账号约束。

## 10. 怎样依次实现与验证这篇设计

先完成 schema 迁移、认证和接入事务，确保一条事件可以得到持久 ACK；再完成归档与 Manifest；接入 Hadoop 详解的作业输出后再写导入、发布和读取。在线接口可以先使用明确标记的固定开发夹具验证 DTO，但不能把夹具当成已运行的集群结果。

合入 develop 后集中核对同批重发、缺号、归档提交中断、发布时隐私重置、旧 run 后完成、两设备水位独立以及同版读取。这些情景分别对应上文具体事务，不扩展成无关的环境异常检测。当前只有设计文档，没有运行 MySQL 迁移、GitHub OAuth、HDFS 归档或服务端测试。
